# TaskMind — Style Guide

## 1. Язык и читаемость

- Код, имена, docstrings, сообщения коммитов и заголовки PR — на английском.
- Комментарий объясняет причину или ограничение, а не пересказывает строку кода.
- Используем понятные предметные названия: `trace_count`, `dataset_id`, `min_support`.
- Избегаем неясных `data2`, `tmp_result`, `manager` и `utils`, если можно назвать конкретную обязанность.

## 2. Python

- Планируемая минимальная версия — Python 3.12. Поддерживаемый диапазон фиксируется в `pyproject.toml` и проверяется в CI при его настройке.
- `snake_case` для функций, модулей и переменных; `PascalCase` для классов; `UPPER_SNAKE_CASE` для констант.
- Абсолютные импорты от `taskmind`; не изменяем `sys.path` для обхода настройки пакета.
- Аннотации типов обязательны у функций и методов основного кода. `Any` допускается только на обоснованной внешней границе с последующей проверкой.
- Публичные функции с нетривиальными правилами имеют docstring: смысл, единицы измерения, ограничения и ошибки.
- Используем `pathlib.Path`, контекстные менеджеры для ресурсов и явный UTF-8 для текста.
- Не используем изменяемые значения по умолчанию в аргументах.
- Предпочитаем небольшие функции. Классы вводим, когда нужны состояние, инварианты или взаимозаменяемое поведение.
- Не вводим универсальную фабрику или базовый класс ради одной реализации без понятной причины.

Пример:

```python
def calculate_support(trace_count: int, total_trace_count: int) -> float:
    """Return the fraction of traces containing at least one occurrence."""
    if total_trace_count <= 0:
        raise ValueError("total_trace_count must be positive")
    if not 0 <= trace_count <= total_trace_count:
        raise ValueError("trace_count must be between zero and total_trace_count")
    return trace_count / total_trace_count
```

## 3. Границы и ошибки

- Соблюдаем зависимости из [architecture.md](architecture.md).
- Алгоритмы не читают окружение, не открывают БД и не печатают результаты пользователю.
- Параметры эксперимента и пороги поступают через конфигурацию. Математические константы не нужно искусственно выносить в YAML.
- Для ошибок входа возвращаем понятное описание поля и причины. Не подавляем исключения через `except Exception: pass`.
- Широкий перехват допустим на границе прикладной операции для записи неуспешного статуса; исходная причина сохраняется, ошибка не превращается в успех.
- `print` допустим для вывода CLI; диагностические сообщения идут через logging.
- Не логируем пароли, токены, полное содержимое полей ввода и персональные данные.
- Для случайности используем переданный генератор или seed, не меняем глобальный random state скрыто.

## 4. Проверки и зависимости

Предлагаемый набор инструментов: `uv`, `pytest`, `ruff`, `mypy`. Версии фиксируются после настройки окружения; не добавляем зависимости только ради наличия технологии в стеке.

После настройки `pyproject.toml`, lock-файла и тестов стандартные команды будут такими:

```bash
uv sync --frozen
uv run ruff check .
uv run ruff format --check .
uv run mypy src/taskmind
uv run pytest
```

Тестируем поведение: границы значений, неправильные данные, несколько вхождений в одной trace, воспроизводимость. Не копируем алгоритм в тест для получения ожидаемого ответа. Для исправления ошибки добавляем минимальный воспроизводящий тест. Для правок только документации достаточно проверки ссылок и примеров.

## 5. Формат коммитов

Используем единый формат:

```text
type[scope]: short description
```

`scope` можно опустить для изменения всего проекта. В описании используем английский глагол в повелительной форме: `add`, `fix`, `remove`, `document`. Первая буква описания строчная, точка в конце не нужна. Рекомендуемая длина заголовка — до 72 символов; подробности выносятся в тело после пустой строки.

| Type | Когда использовать | Пример |
| --- | --- | --- |
| `feat` | Новое поведение | `feat[ingestion]: add JSON event import` |
| `fix` | Исправление ошибки | `fix[discovery]: count each trace once in support` |
| `refactor` | Изменение структуры без смены поведения | `refactor[application]: extract run storage interface` |
| `docs` | Документация | `docs[architecture]: define event contracts` |
| `test` | Только тесты | `test[preprocessing]: cover repeated event identifiers` |
| `perf` | Оптимизация с сохранением поведения | `perf[discovery]: reduce sequence counting allocations` |
| `style` | Только форматирование кода | `style[domain]: apply formatter` |
| `build` | Сборка, упаковка, зависимости | `build: configure Python package and development tools` |
| `ci` | Автоматические проверки | `ci: run lint and tests on pull requests` |
| `chore` | Прочее обслуживание | `chore: update ignored artifact paths` |

Рекомендуемые scopes: `domain`, `ingestion`, `preprocessing`, `discovery`, `modeling`, `automation`, `evaluation`, `application`, `infrastructure`, `cli`, `api`, `simulation`, `demo`, `architecture`.

Примеры плохих заголовков: `update`, `fix stuff`, `final version`, `changes`.

### Один коммит — одно связное изменение

Количество файлов не определяет количество коммитов. Модель события, её проверка и тесты могут составлять один коммит, если вместе добавляют одну возможность. Не связанные с этой возможностью изменения README или форматирование других модулей лучше отделить.

Новый файл сам по себе не требует отдельного коммита. Важнее, чтобы изменение можно было понять и при необходимости отменить целиком.

Пример коммита с объяснением:

```text
fix[discovery]: count each trace once in support

Repeated occurrences within a single trace previously inflated support.
Track unique trace identifiers while retaining the total occurrence count.
```

### Несовместимые изменения

Если изменение ломает принятый внешний контракт, добавляем `!` и объяснение миграции:

```text
feat[domain]!: replace trace activities with structured steps

BREAKING CHANGE: trace consumers must read steps[].activity instead of
activities[]. Regenerate stored traces with the updated preprocessing stage.
```

Не ставим `!` только потому, что изменилось много файлов. Изменение сериализованного контракта также требует обновления версии схемы и документации.

## 6. Данные, секреты и артефакты

- `.env`, токены, виртуальное окружение, caches, большие датасеты и результаты запусков не коммитятся.
- `.env.example` содержит только имена параметров и безопасные примеры.
- Маленькие синтетические fixtures хранятся в `tests/fixtures/`.
- Lock-файл коммитится вместе с изменением зависимостей.
- Ноутбуки не содержат секретов и больших выводов. Основная логика находится в `src/taskmind/`.
- Результаты эксперимента сопровождаются конфигурацией, версиями и seed. Придуманные метрики не публикуются как измеренные.

## 7. Изменение правил

Правила меняются обычным PR с объяснением причины. Настройки formatter/linter в `pyproject.toml` должны соответствовать этому документу. Не смешиваем введение нового стиля с массовой функциональной переработкой.

## 8. Ветки и перенос изменений

В проекте две постоянные ветки:

| Ветка | Назначение |
| --- | --- |
| `dev` | Основная рабочая ветка: сюда коммитим и отправляем код в процессе разработки |
| `main` | Главная ветка: сюда переносим рабочие или завершённые блоки после проверки |

Отдельная ветка для каждой задачи сейчас не обязательна. Незавершённая возможность может находиться в `dev`; её ограничения нужно обозначить в сообщении коммита или описании работы. В `main` не должно попадать случайно сломанное состояние. Завершённая документация или настройка проекта тоже может переноситься в `main`, даже если всё приложение ещё не готово.

Перед началом работы проверяем `git status`. При чистом рабочем дереве:

```bash
git switch dev
git pull --ff-only origin dev
```

После изменения просматриваем diff, добавляем относящиеся к задаче файлы и проверяем staged diff. Пример коммита и отправки:

```bash
git commit -m "feat[ingestion]: add JSON event import"
git push origin dev
```

Если push отклонён из-за новых удалённых коммитов, сначала получаем и объединяем изменения; force push не используем. Не перезаписываем работу другого участника.

### Перенос из dev в main

1. Проверяем, что весь набор изменений `dev`, который попадёт в `main`, готов к переносу.
2. Выполняем доступные проверки. Для документации проверяем текст, ссылки и примеры.
3. Открываем PR: **base — `main`, compare — `dev`**.
4. В описании указываем результат, проверки и оставшиеся ограничения.
5. Просматриваем diff и сливаем через **Create a merge commit**, сохраняя историю постоянной ветки `dev`.
6. Не удаляем `dev`. Обновляем обе локальные ветки:

```bash
git switch main
git pull --ff-only origin main
git switch dev
git merge main
git push origin dev
```

Команды предполагают чистое рабочее дерево. Если Git сообщает о конфликтах или расхождении локальной и удалённой истории, сначала разбираемся с этим состоянием.

PR из `dev` переносит все её изменения относительно `main`, а не только последний законченный блок. Если в `dev` осталась незавершённая работа, обычное слияние откладываем до готовности общего состояния.

Формат `type[scope]: description` применяется к написанным вручную коммитам и заголовкам PR. Автоматические merge-коммиты Git могут сохранять стандартный заголовок.
