# TaskMind — архитектура

## 1. Назначение

TaskMind анализирует журналы пользовательских действий, обнаруживает повторяющиеся последовательности и помогает подготовить их автоматизацию. Проект сочетает обработку событий, исследование алгоритмов и генерацию проверяемых RPA-сценариев.

Первый демонстрационный процесс: поиск клиента в учебной CRM и формирование сводки по его договорам. Все данные искусственные; проверка ботов выполняется в собственном демонстрационном приложении.

Ключевой результат: воспроизводимый путь от файла событий до найденного процесса, исполняемого сценария и отчёта о качестве.

## 2. Объём первой версии

Первая версия включает:

- импорт JSON-журнала с известными границами выполнения задач;
- проверку и нормализацию событий;
- поиск повторяющихся непрерывных последовательностей;
- линейную модель выбранного процесса;
- генерацию Robot Framework-сценария из реализованного каталога действий;
- выполнение сценария в демоприложении и проверку результата;
- отдельную оценку обнаружения на эталонной разметке;
- запуск через CLI и сохранение конфигурации каждого анализа.

Поздние этапы: CSV, самостоятельное выделение задач из общего потока, embeddings и кластеризация, ветвления процессов, HTTP API, PostgreSQL, предложения по восстановлению после ошибок.

В первую версию не входят микросервисы, распределённые очереди, универсальная автоматизация произвольных приложений и генерация произвольного исполняемого кода языковой моделью. Неизвестные шаги нельзя заменять пустыми действиями и выдавать за готовую автоматизацию.

## 3. Архитектурный подход

Используется модульный монолит: один устанавливаемый Python-пакет с явными границами ответственности. Алгоритмы можно запускать без HTTP-сервера и базы данных.

Прикладные операции управляют последовательностью этапов. Вычислительные модули получают данные через аргументы и возвращают типизированные результаты. Чтение, запись и внешние вызовы выполняются через адаптеры.

Направление зависимостей:

- `domain` не импортирует остальные части приложения;
- вычислительные модули используют `domain` и подходящие вычислительные библиотеки;
- `application` использует модули и определяет необходимые интерфейсы хранилищ;
- `infrastructure` реализует эти интерфейсы;
- `interfaces` вызывает прикладные операции;
- `bootstrap.py` связывает конкретные реализации.

Здесь интерфейс хранилища — небольшой Python Protocol при наличии реальной потребности в замене реализации. Абстрактный базовый класс для каждой функции не требуется.

## 4. Структура репозитория

Папки создаются по мере появления реализации. Таблица показывает целевую структуру.

| `src/taskmind/application/` | Прикладные операции, интерфейсы хранилищ и управление этапами |

`domain` содержит только действительно общие понятия. Внутренние структуры конкретного алгоритма остаются в его модуле. Исследовательский ноутбук импортирует основной код, а не хранит его независимую копию.

## 5. Границы модулей

| Модуль | Вход | Выход | Не отвечает за |
| --- | --- | --- | --- |
| ingestion | Файл и версия схемы | Проверенные Event и отчёт импорта | Поиск процессов |
| preprocessing | Event и правила обработки | Trace и отчёт преобразований | Эталонные метки и генерацию ботов |
| discovery | Trace и параметры алгоритма | Pattern с найденными вхождениями | HTTP и сохранение в БД |
| modeling | Выбранный Pattern и исходные последовательности | ProcessModel | Выполнение действий |
| automation | ProcessModel, каталог и параметры запуска | Сценарий либо список неподдерживаемых шагов | Угадывание локаторов и произвольного кода |
| evaluation | Предсказания, отдельный эталон и правила сравнения | Отчёт метрик | Подбор параметров по тестовой выборке |
| application | Команда пользователя | Статус операции и ссылки на артефакты | Реализацию алгоритмов |

## 6. Контракты данных

JSON используется для сериализации. Внутри Python используются типизированные структуры. Точные Python-классы определяются при реализации; приведённые примеры фиксируют смысл полей.

### 6.1. Event

```json
{
  "schema_version": 1,
  "event_id": "evt-001",
  "timestamp": "2026-11-15T10:00:00Z",
  "sequence_number": 1,
  "user_id": "user-017",
  "session_id": "session-042",
  "case_id": "case-008",
  "application": "demo_crm",
  "event_type": "click",
  "element_id": "client_search_button",
  "element_text": "Find client",
  "result": "success"
}
```

Правила версии 1:

- Все поля примера обязательны. `element_text` допускает пустую строку; остальные идентификаторы — непустые строки.
- `timestamp` содержит часовой пояс и приводится к UTC.
- `sequence_number` — целое неотрицательное число, уникальное в пределах сессии. Это порядок источника, позволяющий разрешать одинаковые временные метки.
- `event_type`: `click`, `input`, `navigate`, `export`. Расширение списка требует обновления схемы и документации.
- `result`: `success`, `failure`, `unknown`.
- `event_id` уникален в датасете. Полностью одинаковые повторные записи одного ID сворачиваются с записью в отчёт. Разные записи с одним ID считаются ошибкой.
- `session_id` обозначает период работы пользователя. `case_id` обозначает одно выполнение задачи. Эти понятия не взаимозаменяемы.
- В первой версии каждый case принадлежит одной паре user/session. Межсессионные задачи пока не поддерживаются.
- Значения полей ввода с персональными данными и пароли не собираются. Параметры для тестового бота задаются отдельно.
- Неизвестные поля и версии схемы отклоняются, чтобы опечатки не терялись молча.

Импорт атомарный: при ошибках схема не допускает частичного принятия датасета. Отчёт содержит номер записи, поле и причину без полного дампа пользовательского ввода.

### 6.2. Trace

Trace представляет одно выполнение задачи. Порядок событий определяется временной меткой и затем `sequence_number`; противоречия временного порядка с порядком источника отражаются в отчёте. Для версии 1 такие противоречия отклоняются до анализа.

```json
{
  "schema_version": 1,
  "trace_id": "trace-008",
  "case_id": "case-008",
  "steps": [
    {"activity": "open_client_search", "source_event_ids": ["evt-001"]},
    {"activity": "enter_client_id", "source_event_ids": ["evt-002", "evt-003"]},
    {"activity": "submit_search", "source_event_ids": ["evt-004"]}
  ]
}
```

Несколько событий можно объединить в шаг только по явному правилу. Для каждого шага сохраняются исходные ID. Последовательные одинаковые клики с разными ID автоматически не удаляются: это могут быть повторные попытки.

Нормализация использует версионированное соответствие приложения, типа события и элемента действию. Неизвестное сочетание получает стабильный технический токен на основе этих полей и предупреждение. Эталонный intent для нормализации не используется.

### 6.3. Pattern

```json
{
  "schema_version": 1,
  "pattern_id": "pattern-003",
  "activities": ["open_client_search", "enter_client_id", "submit_search"],
  "trace_count": 80,
  "total_trace_count": 100,
  "support": 0.8,
  "occurrence_count": 92
}
```

`support = trace_count / total_trace_count`: доля последовательностей хотя бы с одним вхождением. `occurrence_count` учитывает все вхождения, включая перекрывающиеся. Полный результат дополнительно содержит список `(trace_id, start_index, end_index)`, где начало включено, конец исключён, индексация начинается с нуля.

Baseline ищет непрерывные фрагменты с настраиваемыми минимальной/максимальной длиной и минимальной поддержкой. Результаты сортируются детерминированно: по убыванию поддержки, затем длины, затем лексикографически по действиям. Пустой датасет отклоняется; отсутствие шаблонов — корректный пустой результат.

### 6.4. ProcessModel и каталог автоматизации

Первая ProcessModel содержит `schema_version`, `process_id`, `source_pattern_id`, упорядоченные шаги с `step_id` и `activity`, а также ссылки на подтверждающие вхождения. Ветвления и циклы в этой версии не выводятся.

Каталог сопоставляет activity с реализованным keyword, типами аргументов, обязательными параметрами, локаторами демоприложения и проверяемым результатом. Локаторы лежат в конфигурации, а не выводятся из похожести текста.

План автоматизации связывает шаги процесса с действиями каталога и параметрами. При неполном соответствии генерация исполняемого сценария прекращается с отчётом. Частичный план можно сохранить как диагностический артефакт, но не как готового бота.

### 6.5. AnalysisRun

Для каждого запуска сохраняются `run_id`, `dataset_id`, контрольная сумма входа, версии схем и правил, алгоритм и параметры, seed, версия кода, признак незакоммиченных изменений, времена начала/окончания, статус, метрики и пути артефактов. При использовании ML добавляются идентификатор и ревизия модели.

Статусы первой версии: `pending`, `running`, `succeeded`, `failed`. Ошибка содержит этап и безопасное описание. Генерация и выполнение бота имеют собственные идентификаторы и статусы: ошибка бота не превращает завершённый анализ в неудачный.

## 7. Прикладные операции

| Операция | Ответственность |
| --- | --- |
| ImportDataset | Проверить вход, записать неизменяемый датасет и отчёт |
| RunAnalysis | Загрузить датасет, выполнить обработку и discovery, сохранить результат |
| BuildProcessModel | Построить модель выбранного кандидата |
| GenerateAutomation | Проверить поддержку шагов и сформировать сценарий |
| ValidateAutomation | Проверить структуру, затем при отдельном запуске выполнение на демоприложении |
| EvaluateRun | Сравнить результат с отдельным эталоном |

Это имена операций, а не требование создать класс для каждой. CLI и будущий API вызывают одинаковые операции. В первой версии выполнение синхронное; очередь задач не требуется.

## 8. Хранение и воспроизводимость

Сначала используется файловый адаптер:

- `data/datasets/<dataset_id>/`: исходный файл, metadata и отчёт импорта;
- `data/runs/<run_id>/`: конфигурация, подготовленные traces, patterns, отчёты;
- `data/automations/<automation_id>/`: модель, сценарий и результаты проверки;
- `data/ground_truth/`: отдельная разметка, доступная только генератору и evaluation.

Пути задаются конфигурацией. Повторный анализ создаёт новый run и не перезаписывает предыдущий. Артефакты записываются сначала во временный файл, затем атомарно заменяют целевой файл в рамках текущего запуска; статус успеха выставляется после успешного сохранения всех результатов.

При добавлении PostgreSQL в нём хранятся метаданные датасетов, запусков и ссылки на артефакты. Необходимость хранения всех событий в таблицах оценивается отдельно. Алгоритмы не получают SQLAlchemy Session.

## 9. Сквозной демонстрационный сценарий

1. Генератор создаёт набор выполнений поиска клиента: основную последовательность, альтернативные действия, ошибки и шум. Seed и параметры сохраняются.
2. Эталонные метки сохраняются отдельно. В анализ передаются события и известные case ID, но не истинный тип процесса.
3. ImportDataset проверяет журнал и создаёт dataset ID.
4. RunAnalysis формирует traces и находит повторяющиеся фрагменты.
5. Пользователь выбирает кандидата; BuildProcessModel создаёт линейное описание.
6. GenerateAutomation проверяет каталог. Параметры тестового клиента подаются отдельно.
7. Сценарий проходит статическую проверку и Robot Framework dry run. Это ещё не доказательство работоспособности.
8. Бот выполняется в демоприложении с подготовленным тестовым состоянием.
9. Проверяется содержимое полученной сводки, а не только отсутствие исключений.
10. EvaluateRun независимо сравнивает обнаруженные процессы с эталоном.

## 10. Оценка качества

Для baseline единица обнаружения — уникальная последовательность действий. На отдельном тестовом наборе генератор формирует эталонный набор непрерывных фрагментов в том же диапазоне длины и с тем же порогом поддержки, исключая вставленные шумовые действия. Это позволяет измерять точность восстановления повторяющихся фрагментов; метрика не означает понимание бизнес-намерения.

Совпадение для версии 1 — точное равенство последовательностей. TP — пересечение найденного и эталонного наборов; FP — найденные вне эталона; FN — пропущенные эталонные. Рассчитываются precision, recall и F1. При нулевом знаменателе метрика возвращает null с причиной, а не вводящее в заблуждение число.

Дополнительно считаются покрытие эталонных выполнений полными целевыми процессами, время анализа и число найденных кандидатов. Длинный фрагмент с высокой поддержкой не объявляется автоматически полезным процессом.

Для автоматизации отдельно измеряются: доля выбранных процессов с полностью поддержанными шагами, доля сгенерированных сценариев, прошедших dry run, и доля выполненных сценариев с правильным итоговым результатом. Для каждой доли публикуются числитель, знаменатель и причины неуспеха.

Для будущей кластеризации ARI/NMI оцениваются по отдельным эталонным меткам; политика обработки шума документируется до эксперимента. Silhouette служит дополнительной оценкой структуры кластеров, а не доказательством правильных намерений.

Данные разделяются по целым выполнениям задач и семействам вариантов, а не по отдельным событиям. Параметры настраиваются на development-наборе. Test-набор содержит отложенные варианты, формулировки и несколько seeds. Синтетические результаты не выдаются за доказательство эффективности на реальных банковских данных. Сравнение с ручной работой требует отдельного измеренного эксперимента.

## 11. Проверки

- Unit: валидация событий, порядок, дедупликация, support, границы вхождений и генерация аргументов.
- Integration: импорт и сохранение датасета, запись run, загрузка каталога, проверка Robot Framework.
- End-to-end: небольшой фиксированный журнал → анализ → выбранная модель → бот → проверка сводки.
- Regression: ранее найденная ошибка получает минимальный воспроизводящий тест.

Тесты не требуют внешнего LLM API. При добавлении моделей отдельно выделяются медленные проверки; обычные тесты используют фиксированные данные или тестовый адаптер.

## 12. Последовательность реализации

| Этап | Проверяемый результат |
| --- | --- |
| 1. Основа | Настроен пакет; Event и JSON reader принимают корректный файл и объясняют ошибки |
| 2. Данные | Генератор воспроизводим; разметка отделена; preprocessing строит traces |
| 3. Baseline | Найдены повторения; support проверен; сохранён отчёт эксперимента |
| 4. Автоматизация | Поддерживаемый процесс исполняется на демоприложении с верным результатом |
| 5. Сравнение | Более сложный алгоритм сравнивается с baseline на том же протоколе |
| 6. Интерфейсы | API и БД добавляются поверх готовых прикладных операций |

Готовность этапа означает работающий проверяемый результат, а не наличие папок.

## 13. Изменение архитектуры

Изменения контрактов, направления зависимостей и протокола оценки обсуждаются в PR и отражаются в этом документе. Существенные решения фиксируются в `docs/decisions/NNNN-short-title.md`: проблема, варианты, выбранное решение, последствия.

До реализации необходимо отдельно выбрать интерфейс демоприложения, библиотеку взаимодействия бота с ним и конкретную embedding-модель для сравнительного этапа. Эти решения не блокируют импорт и baseline.

Правила оформления, коммитов и работы с ветками `dev` и `main`: [style-guide.md](style-guide.md).
